Lesson 02 · micrograd

DAG ไม่ใช่ tree

คำเดียวที่ใช้ผิดตั้งแต่ต้น แล้วทำให้เข้าใจ backpropagation ผิดไปทั้งหมด — และเหตุผลว่าทำไม “node ที่ถูกใช้ซ้ำ” คือใจกลางของเรื่องนี้

2026-08-08 · Day 2 · M1 micrograd

คำถามที่ดูเล็กแต่ไม่เล็ก

เขียนนิพจน์ที่ตัวแปรตัวหนึ่งถูกใช้สองที่:

x = Value(2.0)
y = Value(-3.0)
z = x * y + x        # x โผล่สองครั้ง

กราฟของ z มี x สองกล่อง หรือ กล่องเดียวที่มีลูกศรออกสองเส้น?

คำตอบ: กล่องเดียว — และพิสูจน์ได้

left_x  = z._prev[0]._prev[0]   # x ที่อยู่ใต้ (x*y)
right_x = z._prev[1]            # x ที่ถูกบวกตรงๆ

left_x is right_x     # True
id(left_x) == id(right_x)   # True

x ถูกสร้างครั้งเดียวด้วย Value(2.0) แล้วชื่อ x ถูกใช้อ้างถึงมันสองที่ — Python ไม่ได้ก๊อป object ให้ มันคือก้อนเดิม

กราฟจริงคือ 4 node / 4 edge:

nodes:  x, y, (x*y), z

edges:  x     → (x*y)      ← x เส้นที่ 1
        y     → (x*y)
        (x*y) → z
        x     → z          ← x เส้นที่ 2

นิยามที่ทำให้ทุกอย่างชัด

เงื่อนไขตรงนี้เป็นไหม
Tree ทุก node มีพ่อแม่ได้ไม่เกิน 1 ตัว ❌ x มีพ่อแม่ 2 ตัว
DAG มีทิศทาง ไม่มีวงจร แต่มาบรรจบกันได้ ✅ ใช่
ทำไมต้องแยกให้ออก

“การมาบรรจบกัน” ไม่ใช่รายละเอียดปลีกย่อย — มันคือเรื่องทั้งหมดของ micrograd ในโครงข่ายจริง น้ำหนักทุกตัวถูกใช้ซ้ำหลายที่เสมอ ถ้ายังคิดว่าเป็น tree อยู่ จะเข้าใจ backpropagation ผิดตั้งแต่ฐาน

เพราะฉะนั้น “เดินซ้ำ” จึงต้องแก้ — สามเหตุผล

1. เพราะมันไม่ตรงกับความจริง

ถ้าถามว่า “กราฟนี้มี node อะไรบ้าง” แล้ว x โผล่สองครั้ง คำตอบก็ผิดตั้งแต่ต้น ไม่ต้องรอให้เกิดผลเสียอะไร

ข้อควรระวัง: รูปที่วาดออกมาจะยังสวยอยู่ เพราะ graphviz ใช้ชื่อ node เป็นตัวระบุ สั่งซ้ำชื่อเดิมมันแค่เขียนทับ — รูปถูกไม่ได้แปลว่าโครงสร้างข้อมูลถูก

2. เพราะมันระเบิดแบบ exponential

วัดจริงกับกราฟที่แต่ละชั้นใช้ node ก่อนหน้าซ้ำสองครั้ง (v = v + v):

3. เพราะ backprop — เก็บไว้ค้นพบเอง

คำทำนายที่จดไว้ ยังไม่เฉลย

ถ้า x โผล่สองครั้งในลิสต์ที่ใช้ไล่เรียก _backward() แล้วเราวนตามลิสต์นั้น —

  • _backward ของ x จะถูกเรียกกี่ครั้ง?
  • gradient ของ x จะออกมากี่เท่าของค่าที่ถูกต้อง?
  • ถ้าโผล่สามครั้งล่ะ?

บั๊กแบบนี้ไม่ crash ไม่ช้า ไม่มีอะไรผิดปกติให้เห็น — มันแค่ให้ตัวเลขที่ผิดแบบเงียบๆ ซึ่งอันตรายกว่าสองข้อบนมาก

เก็บ node ด้วยอะไร: list หรือ set

ถ้าคำถามคือ “มี node อะไรบ้าง” และห้ามซ้ำ → set ตรงกับความหมายพอดี (เพิ่มด้วย .add() ไม่ใช่ .append())

ทำงานได้เพราะ Value เป็น hashable โดยอัตโนมัติ — Python ใช้ identity เป็น hash ให้ แต่เมื่อไหร่ที่เขียน __eq__ Python จะถอด __hash__ ออกทันที แล้วทั้งระบบจะพังด้วย TypeError: unhashable type

set ไม่มีลำดับ — และตอนนี้ยังไม่เป็นไร

ใส่ตามลำดับ a, b, c, d, e เป๊ะๆ แล้ววนออกมา:

set  : [e, a, d, c, b]      ← เรียงตาม hash ทำนายไม่ได้
list : [a, b, c, d, e]
dict : [a, b, c, d, e]      ← dict รับประกันลำดับตั้งแต่ Python 3.7

งานตอนนี้คือตอบว่า “มีอะไรอยู่ในถุงบ้าง” ไม่ใช่ “เรียงยังไง” วาดกราฟจะสั่ง node ตัวไหนก่อนก็ได้ รูปออกมาเหมือนกัน → set ถูกต้องแล้วสำหรับตอนนี้

หลักการที่ต้องเก็บไว้

“เคยเจอยัง?” กับ “ลำดับที่เท่าไหร่?” เป็นคำถามคนละข้อ และมักต้องใช้ที่เก็บคนละอัน — set ตอบข้อแรกได้เร็วมากแต่ตอบข้อสองไม่ได้เลย ส่วน list ตรงกันข้าม ตอน backward จะต้องการคำตอบทั้งสองข้อพร้อมกัน และนั่นคือเหตุผลที่ topological sort มีอยู่บนโลก

บทเรียนที่ใหญ่ที่สุดของหน้านี้

การใส่ set ให้ที่เก็บ ไม่ได้ แก้เรื่องเดินซ้ำ — มันแก้แค่ “การเก็บ” ส่วน “การเดิน” ยังลงไปที่ node เดิมซ้ำอยู่ดี งานวัดผลยืนยัน: 19 node แต่ยังเดิน 524,287 ครั้ง และ edge ออกมาซ้ำ

แยกให้ออก

dedup ที่ตัวเก็บ ≠ dedup ที่การเดิน — การ์ดกันเดินซ้ำต้องอยู่ที่ตัว recursion ไม่ใช่ที่ container

ตรวจตัวเอง

  1. ทำไม Value(2.0) สองตัวที่คนละที่ในกราฟ ต้อง เป็นคนละ node?
  2. สำหรับ w = (p*q) + (p*q) โดยที่ e = p*q; w = e + e — กราฟมีกี่ node และกี่ edge ที่ไม่ซ้ำ?
  3. ถ้ากราฟเป็น tree จริงๆ (ไม่มี node ถูกใช้ซ้ำเลย) เรื่อง gradient accumulation จะยังจำเป็นไหม?
