Lesson 03 · micrograd

Recursion, closure และการเดินกราฟ

วิธีคิดกับ recursion ที่ไม่ต้องไล่การทำงานในหัว — บวกกับกลไก closure ที่จะกลับมาอีกครั้งตอนเขียน _backward

2026-08-08 · Day 2 · M1 micrograd

ทำไม while loop ใช้ไม่ได้

ความพยายามแรกคือเดินกราฟด้วย while:

while root._prev != []:
    ...  # ไม่มีบรรทัดไหนเปลี่ยนค่า root

ผลคือลูปไม่มีวันจบ — และมันชี้ไปที่ปัญหาที่ลึกกว่านั้น: ไม่รู้ล่วงหน้าว่ากราฟลึกกี่ชั้น เพราะฉะนั้นเขียนลูปตายตัวไม่ได้

แต่มีสิ่งหนึ่งที่รู้แน่: ทุก node ทำงานเหมือนกันหมด ไม่ว่าจะอยู่ชั้นไหน — นั่นคือสัญญาณว่าต้องใช้ recursion

กรอบคิด 4 ข้อ

ความรู้สึกว่า recursion “ยาก” มาจากการพยายามไล่การทำงานในหัว ซึ่งเกินความจำระยะสั้นของมนุษย์ ใช้กรอบนี้แทน:

  1. สัญญา (contract) — เขียนเป็นประโยคก่อนแตะคีย์บอร์ด: “f(x) คืน ______ ของกิ่งที่มี x เป็นยอด”
  2. Base case — เคสไหนตอบได้ทันทีโดยไม่ต้องถามใคร
  3. Recursive case — สมมติว่า f(ลูก) ทำงานถูกต้องสมบูรณ์แล้ว ฉันต้องเพิ่มอะไร
  4. รวม — ผลจากลูกหลายตัว + ของตัวเอง = คำตอบที่ตรงกับสัญญาข้อ 1
ข้ามข้อ 1 = บั๊กที่หายาก

บั๊กสองตัวแรกที่เจอวันนี้มาจากการไม่เขียนสัญญาไว้ก่อน: base case คืน [] (ทิ้ง node ตัวเองไป) ส่วน recursive case เอา list ทั้งก้อนไป append เป็นสมาชิกเดียว (ได้ list ซ้อน list) — base case กับ recursive case คืนของคนละชนิดกัน

การกระโดดด้วยศรัทธา

ตอนเขียนข้อ 3 ให้เชื่อว่า f(ลูก) ทำงานถูกแล้ว ห้ามไล่เข้าไปดูข้างใน ฟังดูเหมือนโกง แต่ไม่โกง เพราะพิสูจน์แค่สองอย่าง: base case ถูก และ ถ้าลูกถูกแล้วพ่อถูก

นี่คือ induction เป๊ะๆ — เหมือนพิสูจน์ stability ด้วยการแสดง initial condition แล้วแสดง step โดยไม่ต้องไล่ทีละ k

และมันคือรูปเดียวกับ Bellman equation: V(s) = r(s) + Σ V(s′) — ไม่มีใครไล่คำนวณ V ทุก state ในหัว ทุกคนเชื่อสมการ การเดินกราฟก็อ่านแบบเดียวกัน

สะสมผลลัพธ์ได้ 3 แบบ — ไม่มีแบบไหนต้องใช้ global

แบบวิธีค่าไหลทางไหนแต่ละ call คืนอะไร
Aคืนค่าขึ้นไป พ่อแม่เอามารวมขึ้นคำตอบสมบูรณ์ของกิ่งตัวเอง
Bส่งตะกร้าลงไปเป็น argumentลงNone
Cฟังก์ชันซ้อนฟังก์ชัน + closureลงNone (side effect)

factorial ที่ทุกคนรู้จักคือแบบ A อยู่แล้ว — ทุก call คืนคำตอบของตัวเองขึ้นไป ไม่มีตะกร้ากลาง: 

def fact(n):
    if n <= 1:
        return 1                 # base: ตอบเองได้
    return n * fact(n - 1)       # รวม: ของฉัน × ของลูก

ตัวเดียวกันเขียนแบบ C:

def fact(n):
    result = 1                   # ตะกร้า

    def go(k):
        nonlocal result          # ต้องใส่! เพราะ result *= k คือ assign ทับ
        if k <= 1:
            return
        result *= k
        go(k - 1)

    go(n)
    return result
ทำไมเลือก C สำหรับกราฟ

แบบ A ต้อง “รวม” ผลของลูกทุกครั้ง ซึ่งเป็นจุดที่พลาดง่าย (บั๊ก list ซ้อน list) ส่วนแบบ C ทุกคน add ทีละตัวลงตะกร้าเดียวกัน จึงไม่มีปัญหานั้นเลย — นี่คือเหตุผลที่ Karpathy ใช้แบบ C

ทำไมเรียกว่า “closure”

Free variable คือชื่อที่ฟังก์ชันใช้ แต่ไม่ได้นิยามเองและไม่ได้รับมาเป็น argument

ฟังก์ชันที่มีตัวแปรลอยแบบนี้เรียกว่า “เปิด” (open) เพราะเอาไปรันเดี่ยวๆ ไม่ได้ Python จึง “ปิด” (close over) มันให้ — แนบกล่องที่ชี้ไปตัวแปรของ scope ข้างนอกติดตัวไปด้วย ฟังก์ชันที่ถูกปิดแล้วเรียกว่า closure

ดูของจริงได้ ไม่ใช่คำเปรียบเปรย:

free variables ที่ f ใช้แต่ไม่ได้นิยามเอง : ('nodes',)
กล่องที่ f แบกติดตัวไป                    : (<cell at 0x...: list object at 0x...>,)
ข้างในกล่องคือ                            : []

ฟังก์ชันธรรมดาไม่มี closure               : None | freevars: ()

f.__closure__ และ f.__code__.co_freevars

เส้นแบ่งของ nonlocal

เขียนอะไรคืออะไรต้อง nonlocal ไหม
bucket.append(x)แก้ของในกล่องเดิมไม่ต้อง

ทำไมต้องเข้าใจตอนนี้

อีกไม่กี่วัน _backward ของแต่ละ operation จะเป็น closure ที่แบก self, other และ out ติดตัวไปในกล่องแบบเดียวกันเป๊ะ — เจอ closure ครั้งแรกตอนเขียน viz ดีกว่าเจอครั้งแรกตอนเขียน backward เพราะตอนนี้ถ้าพังจะเห็นด้วยตา ตอนนั้นถ้าพังจะเห็นแค่ตัวเลข gradient ผิด

ตั้งชื่อ node ให้ graphviz: id() ไม่ใช่ hash()

graphviz ต้องการ ชื่อภายในที่ไม่ซ้ำ (ผูกลูกศร) แยกจาก ป้ายที่คนเห็น ใช้ค่า data เป็นชื่อไม่ได้ เพราะสอง node อาจมีค่าเท่ากันพอดี แล้วกราฟจะยุบมันเป็นตัวเดียว

คำตอบคือ id() ซึ่งการันตีว่าไม่ซ้ำ ในบรรดา object ที่ยังมีชีวิตอยู่พร้อมกัน (แปลงเป็น string ก่อน)

แล้วทำไมไม่ใช้ hash()

ตอนนี้ hash() ใช้ได้จริง เพราะ CPython คำนวณมันจาก id ตรงๆ:

id(a)     = 1415573106912
hash(a)   = 88473319182
id(a) >> 4 == hash(a)   → True

แต่สองฟังก์ชันนี้สัญญาคนละเรื่อง — id สัญญาเรื่องตัวตน (“นี่คือ object ก้อนไหน”) ส่วน hash สัญญาเรื่องความเท่ากัน (“อะไรที่เท่ากันต้องได้ค่าเท่ากัน”)

วันที่เขียน __eq__ ให้เทียบด้วย data — ซึ่งเป็นเรื่องปกติมาก — Value(2.0) สองตัวคนละที่จะกลายเป็น “ตัวเดียวกัน” ในสายตา hash แล้วกราฟจะผิดโดยไม่มี error ให้เห็น
