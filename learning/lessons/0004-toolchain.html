เครื่องหนึ่งเครื่องมี Python ได้หลายตัว

ผลการตรวจเครื่องจริงในวันแรก:

Pythonเวอร์ชันมีอะไร
.venv ของโปรเจกต์3.13.13pip ตัวเดียว ← Jupyter ใช้ตัวนี้
system3.14.3pytest, numpy, pandas
conda base—package ที่เพิ่งลงไปทั้งหมด

อาการ: ลง ipykernel สำเร็จ แต่ VS Code ยังบอกว่าหาไม่เจอ เพราะมันไปลงที่ conda base ไม่ใช่ venv ของโปรเจกต์

สาเหตุ: Anaconda ติดตั้ง hook ที่ auto-activate base ทุกครั้งที่เปิดเทอร์มินัลใหม่ conda จึงแย่ง PATH ไปก่อน แล้ว pip ที่เรียกก็คือ pip ของ conda

เครื่องมือวินิจฉัย

python -c "import sys; print(sys.executable)"

ถ้ามีคำว่า conda / anaconda3 / miniforge ในเส้นทาง — นั่นคือสาเหตุ

python -m และวิธีที่กันพลาด 100%

python -m NAME แปลว่า “หา module ชื่อ NAME ด้วยกลไก import ปกติ แล้วรันมันในฐานะ __main__”

ผลที่วัดได้จริงจากไฟล์เดียวกัน เรียกสองแบบ:

python demo/sub/probe.py    →  sys.path[0] = ...\demo\sub    (โฟลเดอร์ของไฟล์)
python -m demo.sub.probe    →  sys.path[0] = ...\           (โฟลเดอร์ปัจจุบัน)
คำสั่งทำไมต้องเป็นแบบนี้
python -m pip install Xpip เฉยๆ คือ .exe บน PATH ไม่รู้ว่าผูกกับ Python ตัวไหน — -m การันตีว่าเป็น pip ของ Python ตัวที่รันคำสั่งนี้
python -m pytestใส่ cwd ลง sys.path ทำให้ from micrograd import ... ในเทสต์หาเจอ — pytest เฉยๆ ไม่ใส่
python -m venv .venvสร้าง venv ด้วย Python ตัวที่เจาะจง
python -m timeit "..."จับเวลาโค้ดสั้นๆ อย่างน่าเชื่อถือ
กฎที่กันพลาดที่สุด

เลิกพึ่ง activate ไปเลย — ระบุ path ของ interpreter ตรงๆ แล้วใช้ -m: .venv\Scripts\python.exe -m pip install ... ไม่ว่า PATH จะเละแค่ไหนก็ไม่มีทางผิดตัว

requirements.txt ที่ดูปกติแต่ใช้ไม่ได้

รัน pip freeze ผิดตัว แล้วได้ไฟล์หน้าตาแบบนี้:

Brotli @ file:///D:/bld/brotli-split_1764017006836/work
certifi @ file:///home/conda/feedstock_root/build_artifacts/...
torch==2.13.0

บรรทัด @ file:/// ชี้ไปที่ path บนดิสก์ของเครื่องที่ build conda package ซึ่งไม่มีอยู่บนเครื่องใครเลยในโลก ใครก็ตามที่ clone repo แล้วรัน pip install -r requirements.txt จะพังทันที — ทำลายเหตุผลทั้งหมดที่มีไฟล์นี้

pip freeze ให้ผลตาม Python ตัวที่รันมัน — freeze ผิดตัว ได้ไฟล์ผิดทั้งไฟล์

Graphviz: ลงแล้วแต่ยังใช้ไม่ได้

graphviz ใน pip เป็นแค่คนเขียนใบสั่ง คนวาดจริงคือโปรแกรม dot.exe ที่ต้องลงแยก และ installer ไม่ได้ติ๊ก “Add to PATH” มาให้: 

C:\Program Files\Graphviz\bin\dot.exe    ← ไฟล์อยู่ครบ
MACHINE PATH: no Graphviz                 ← แต่ไม่มีใน PATH
USER PATH:    no Graphviz

เปิดเทอร์มินัลใหม่กี่ครั้งก็ไม่ช่วย เพราะปัญหาไม่ใช่ PATH ค้าง แต่คือไม่เคยถูกใส่เลย และเมื่อแก้ PATH แล้วต้องปิด VS Code เปิดใหม่ทั้งโปรแกรม ไม่ใช่แค่ restart kernel — เพราะ kernel รับ PATH ต่อมาจาก VS Code อีกที

อาการที่ควรจำ

import graphviz ผ่านปกติ แต่พังตอน render ด้วย ExecutableNotFound — เพราะ package กับ binary เป็นคนละอย่างกัน

Git: กราฟของ snapshot ไม่ใช่กองไฟล์

Git เก็บ snapshot ทั้ง tree แล้วผูกกันเป็น DAG — commit แต่ละตัวมี pointer ชี้ไป parent

สามพื้นที่

พื้นที่คืออะไรย้ายเข้าด้วย
Working directoryไฟล์จริงบนดิสก์(แก้ไฟล์)
Staging areaสำเนาที่จะเข้า commit ถัดไปgit add
Repositoryประวัติถาวรgit commit

git add คัดลอกเนื้อไฟล์ ณ วินาทีนั้น ไม่ใช่แค่จดชื่อไฟล์ไว้ — ถ้าแก้ต่อโดยไม่ add ซ้ำ commit จะได้เวอร์ชันเก่า และไฟล์เดียวกันจะโผล่สองที่พร้อมกันใน git status

คำสั่งเทียบอะไรกับอะไร
git diffดิสก์ ↔ staging — สิ่งที่แก้แล้วแต่ จะไม่ เข้า commit
git diff --stagedstaging ↔ commit ล่าสุด — สิ่งที่ จะ เข้า commit จริง

พิมพ์ git diff --staged ก่อน commit ทุกครั้ง = ไม่มีวัน commit ผิดเวอร์ชัน

กฎข้อเดียวของการแก้ประวัติ

แก้ประวัติที่ยังไม่ push ได้อย่างอิสระ — ห้ามแก้ประวัติที่ push ไปแล้วและมีคนดึงไปแล้ว

git commit --amend ไม่ได้แก้ commit เดิม — commit ใน Git แก้ไม่ได้ เพราะ hash คำนวณจากเนื้อหา สิ่งที่เกิดจริงคือ Git สร้าง commit ใหม่ที่มี parent เดียวกัน แล้วเลื่อน pointer ของ branch มาชี้ตัวใหม่: 

ก่อน:   8e827df ──── fc688b6  ← main   (requirements เสีย)

หลัง:   8e827df ──── fc688b6           (ลอยอยู่ ไม่มีใครชี้ถึง)
             └────── 2a23c41  ← main   (requirements ถูก)

เกือบทุกคำสั่งของ Git คือ “สร้าง node ใหม่ + เลื่อน pointer” ไม่ใช่ “แก้ของเดิม” — รูปเดียวกับ computation graph พอดี

ตาข่ายนิรภัย: git reflog จดทุกการเคลื่อนไหวของ pointer ไว้ราว 90 วัน กู้ commit ที่ “หายไป” กลับมาได้เสมอ

origin กับ origin/main เป็นคนละอย่าง

pointerอยู่ที่ไหนคืออะไร
mainเครื่องเราcommit ล่าสุดของเราจริงๆ
origin/mainเครื่องเราค่าที่จำไว้ว่าตอนคุยกับ GitHub ครั้งล่าสุด main ฝั่งโน้นอยู่ตรงไหน
main บน GitHubเซิร์ฟเวอร์ของจริงฝั่งโน้น

origin/main คือ estimate ของ state ฝั่ง remote ที่อัปเดตเฉพาะตอน fetch / pull / push — ระหว่างนั้นมันคือค่าค้าง ไม่มี continuous observation นี่คือเหตุผลที่ git status บอก ahead/behind ได้โดยไม่ต้องต่อเน็ต และเป็นเหตุผลที่ข้อมูลนั้นอาจล้าสมัย
