Lesson 05 · gradient

grad ที่ไหลย้อนกลับ
และเหตุผลที่ลำดับสำคัญ

วันที่กราฟหยุดเป็นแค่โครงสร้างข้อมูล แล้วเริ่มคำนวณอะไรบางอย่างได้จริง — สามความคิดที่ต้องมาเรียงกัน: grad คือของใคร, ใครเป็นคนอัปเดต, และทำไมสลับลำดับแล้วพัง

2026-08-09 · Day 3 · เฟส 1 ขั้น 1–6

grad ไม่ใช่ “อนุพันธ์” เฉยๆ — มันมีเจ้าของสองฝั่ง

กับดักแรกของทั้งบทคือคำว่า grad สั้นเกินไปจนหลอก a.grad ไม่ได้แปลว่า “อนุพันธ์ของ a” — อนุพันธ์เทียบกับอะไรล่ะ?

นิยามที่ต้องท่องให้ขึ้นใจ

a.grad คือ ∂(output ตัวสุดท้าย) / ∂a
แปลเป็นภาษาคน: “ถ้าขยับ a ขึ้นนิดนึง ผลลัพธ์ปลายทางจะขยับไปเท่าไหร่”

สังเกตว่านิยามนี้อ้างถึง node สองตัวเสมอ — ตัวที่เก็บค่า (a) และ ตัวปลายทางที่ไม่ได้ถูกเอ่ยชื่อ (root ของกราฟ) ตัวปลายทางไม่ได้ถูกเก็บไว้ใน Value ที่ไหนเลย มันถูก เลือก ตอนที่เริ่ม backward pass ต่างหาก

นั่นคือเหตุผลที่ต้องตั้ง root.grad = 1.0 ก่อนเดินย้อนกลับ — ไม่ใช่ค่าที่ตั้งลอยๆ แต่คือ ∂root/∂root = 1 ซึ่งเป็นการ ประกาศว่า “ปลายทางคือตัวนี้” ให้ทั้งกราฟรู้ เปลี่ยน root ก็เปลี่ยนความหมายของ grad ของทุก node ในกราฟทันที

คิดด้วยมือก่อน แล้วโค้ดจะตามมาเอง

กราฟที่ใช้ทั้งวัน:

a = 2.0     b = -3.0     c = 10.0
e = a * b               →  -6.0
d = e + c               →   4.0

ไล่จากปลายทางย้อนกลับ ทีละขั้น ขั้นละหนึ่งบรรทัด:

ถามได้มาจากไหน
∂d/∂d1นิยาม — ตัวเองเทียบตัวเอง
∂d/∂c1d = e + c → + ส่งต่อเท่าเดิม
∂d/∂e1เหมือนกัน
∂d/∂a−3∂d/∂e · ∂e/∂a = 1 · b
∂d/∂b2∂d/∂e · ∂e/∂b = 1 · a

สองแถวล่างคือ chain rule ล้วนๆ และมีรูปเดิมเสมอ: gradient ที่ไหลมาจากข้างบน × อนุพันธ์เฉพาะที่ของ operation ตัวนี้

กฎประจำ operation — derive เองได้ ไม่ต้องจำ
  • + เป็น ท่อส่งต่อ — gradient ผ่านไปเท่าเดิมทั้งสองขา (∂(x+y)/∂x = 1)
  • * เป็น ตัวสลับ — แต่ละขาได้ gradient คูณด้วยค่าของอีกขา (∂(x·y)/∂x = y)

บั๊กที่โผล่ตรงนี้พอดี

สูตรที่เขียนไว้ตอนแรกคือ y.grad += x.data — หายไปหนึ่งตัวคูณ ตัวที่ควรอยู่คือ gradient ที่ไหลมาจากข้างบน มันผ่านเทสต์แรกได้เพราะบังเอิญ w.grad == 1 พอดี — คูณด้วย 1 ก็เหมือนไม่ได้คูณ

เทสต์ที่จับได้ ต้องเป็นเทสต์ที่ gradient ข้างบนไม่เท่ากับ 1:

x = 3.0   y = 2.0
z = x * y        →  6.0
q = z * z        → 36.0     ← gradient ที่ไหลลงมาที่ z คือ 2z = 12  ไม่ใช่ 1

ของจริง (ตรงกับ numerical):   ∂q/∂x = 12·y = 24     ∂q/∂y = 12·x = 36
สูตรที่ขาดตัวคูณ:                       y  =  2                x  =  3
บทเรียนเรื่องการทดสอบ

เทสต์ที่ทุกตัวแปรเป็น 1 หรือ 0 คือเทสต์ที่มองไม่เห็นบั๊กเรื่องการคูณ เลือกตัวเลขที่คูณกันแล้วได้ผลต่างกันเสมอ — และเป็นเหตุผลที่ numerical gradient คุ้มค่ามาก มันไม่รู้อะไรเกี่ยวกับโค้ดเลย จึงไม่ผิดพลาดตามกันไปด้วย

ใครเป็นคนอัปเดต grad ของใคร

คำถามที่ตอบถูกในวันนี้ และเป็นแกนของทั้งระบบ:

node แต่ละตัว ไม่ได้คำนวณ grad ของตัวเอง — มันคำนวณ grad ให้ ลูกๆ ของมัน

เพราะ node ที่รู้ว่า operation คืออะไร คือ node ผลลัพธ์ ไม่ใช่ node input e รู้ว่าตัวเองเกิดจาก a * b — a ไม่รู้เลยว่าถูกเอาไปทำอะไรต่อ ดังนั้น e._backward() คือคนที่มีข้อมูลครบสำหรับกรอกค่าลงใน a.grad และ b.grad

ผลข้างเคียงสองข้อที่ตามมาทันที และตอบไปแล้ววันนี้:

คำถามคำตอบ
Leaf node ต้องมี _backward ไหม มีได้ แต่มันต้องไม่ทำอะไรเลย — leaf ไม่มีลูกให้ส่งต่อ (จึงตั้งเป็น lambda: None ไว้ใน __init__ แล้วให้ operation ไปเขียนทับ)
เรียก d._backward() แล้วมันเดินต่อทั้งกราฟเลยไหม ไม่ — มันขยับแค่หนึ่งขั้น คือกรอก grad ให้ e กับ c แล้วจบ ที่เหลือต้องมีใครสักคนเรียก e._backward() ต่อ นั่นคืองานของ backward()

ทำไมต้องเป็น closure ไม่ใช่ method

_backward ต้องรู้จัก node สามตัว พร้อมกัน: ผลลัพธ์ กับ input ทั้งสองขา ซึ่งเป็นข้อมูลที่มีอยู่ครบตอนสร้าง node เท่านั้น

Closure เก็บสามตัวนั้นเอาไว้ได้ฟรี — ฟังก์ชันที่ประกาศอยู่ข้างใน __mul__ มองเห็นตัวแปรใน scope นั้นตลอดไป แม้ __mul__ จะ return ไปนานแล้ว ตรวจได้จริงด้วย f.__code__.co_freevars

Python ที่เรียนแถมมาวันนี้

บรรทัด t._backward = _backward ต้องอยู่หลัง def เพราะบรรทัดนั้นอ่านค่าชื่อ _backward ทันที แต่ เนื้อใน ของฟังก์ชันอ้างชื่อที่ยังไม่มีตัวตนได้ — ชื่อในเนื้อฟังก์ชันถูกหาตอนเรียก ไม่ใช่ตอนประกาศ สองอย่างนี้คนละเวลากัน และเป็นที่มาของ error งงๆ ทั้งหมดตรงนี้

ทำไมต้อง += ไม่ใช่ =

นี่คือความคิดที่ลึกที่สุดในทั้ง micrograd และเป็นบั๊กที่คนทำพลาดมากที่สุด เหตุผลไม่ได้อยู่ใน Python — มันอยู่ในแคลคูลัส

ดูกราฟ z = x*y + x — x ปรากฏสองที่:

       x ──┐
           ├──→ w = x*y ──┐
       y ──┘              ├──→ z = w + x
       x ─────────────────┘        ↑
       └── เส้นทางที่สอง มาบรรจบกันที่ z

Chain rule แบบหลายตัวแปร บอกว่า เมื่อตัวแปรหนึ่งส่งผลถึงปลายทางได้หลายเส้นทาง อนุพันธ์รวมคือ ผลบวกของทุกเส้นทาง: 

dz/dx  =  ∂z/∂x  +  ∂z/∂w · dw/dx
       =    1     +    1   ·   y

ทีนี้ backward pass เดินทีละ operation — มันไม่เคยเห็นสองเส้นทางพร้อมกัน มันเห็นทีละเส้น เครื่องหมาย + ในสูตรข้างบนจึงต้องถูกทำให้เกิดขึ้นด้วย += ในโค้ด — แต่ละเส้นทางมาถึงคนละเวลา แล้วบวกสะสมไว้ที่ node

ถ้าใช้ = จะเกิดอะไรขึ้น

เส้นทางที่มาทีหลัง เขียนทับ เส้นทางที่มาก่อน ผลคือได้ gradient ของเส้นทางเดียว แทนที่จะเป็นผลรวม — ค่าออกมาเป็นตัวเลขที่ดูสมเหตุสมผล ไม่มี error ไม่มี crash แค่โมเดลเทรนไม่ลง แล้วหาสาเหตุไม่เจอ

เทสต์ที่สั้นที่สุดที่จับเรื่องนี้ได้ — และผ่านแล้ว:

x = Value(3.0)
z = x + x          # dz/dx = 2
z.grad = 1.0
z._backward()
x.grad   →  2.0    #  ถ้าเป็น "="  จะได้ 1.0

สอง node เดียวกัน สองครั้งใน _prev ทั้ง self และ other ชี้ไปที่ object เดียวกัน — เขียน += จึงได้ 1+1 = 2 ตามที่ควรเป็น

การทดลองที่พิสูจน์ว่าลำดับสำคัญ

เรียก _backward() ด้วยมือทีละตัวบนกราฟ d = a*b + c สองรอบ:

ลำดับa.gradb.gradเกิดอะไรขึ้น
d ก่อน แล้ว e −32 ถูก — ตอน e ทำงาน e.grad เป็น 1 แล้ว
e ก่อน แล้ว d 00 ผิด — ตอน e ทำงาน e.grad ยังเป็น 0.0 อยู่ a.grad += 0 * b.data จึงได้ศูนย์

จุดที่ต้องสังเกตให้ดี: รอบที่สอง ไม่มี exception ไม่มี warning โปรแกรมรันจบสวยงาม แล้วให้คำตอบที่ผิด นี่คือรูปแบบความผิดพลาดที่แพงที่สุดใน ML

Invariant ที่นิยามคำว่า “ลำดับที่ถูก”

node หนึ่งจะเรียก _backward() ได้ ก็ต่อเมื่อ grad ของมันครบแล้ว — และ grad จะครบก็ต่อเมื่อ พ่อแม่ทุกตัว ของมันทำงานไปหมดแล้ว
พูดสั้นๆ: พ่อต้องมาก่อนลูกเสมอ ไม่มีเงื่อนไขอื่น

บนกราฟ 5 node เรียงเองได้ในหัว บนกราฟ 500 node เรียงเองไม่ได้ — และนั่นคือทั้งหมดที่ topological sort มีไว้ทำ ไม่ใช่อัลกอริทึมลึกลับ แต่เป็นคำตอบของคำถามว่า “แล้วใครควรทำงานก่อนใคร”

วิธีเช็คว่าลำดับที่ได้ถูกจริงไหม ไม่ต้องดูด้วยตา — เช็คด้วย property เดียวนี้ ซึ่งใช้ได้กับกราฟทุกรูปทรง: 

pos = {id(n): i for i, n in enumerate(order)}
for child, parent in edges:
    assert pos[id(parent)] < pos[id(child)]
