โจทย์: หาลำดับที่ทำให้ invariant เป็นจริง

Invariant ที่นิยามคำว่า “ลำดับที่ถูก”

node จะเรียก _backward() ได้ ก็ต่อเมื่อ grad ของมันครบแล้ว = พ่อแม่ทุกตัวเรียกไปหมดแล้ว
พูดสั้นที่สุด: พ่อต้องมาก่อนลูกเสมอ ไม่มีเงื่อนไขอื่น

Topological sort ไม่ใช่อัลกอริทึมลึกลับ — มันคือคำตอบของคำถามเดียวว่า “แล้วใครควรทำงานก่อนใคร” บนกราฟ 5 node เรียงเองได้ในหัว บนกราฟหมื่น node เรียงเองไม่ได้ จบแค่นั้น

ทำไมกราฟที่ใช้มาตลอดถึงไม่เคยพัง

กราฟ d = a*b + c สลับลำดับยังไงก็เห็นปัญหาไม่ชัด และ z = x*y + x ก็เกือบไม่เห็น เหตุผลคือกับดักที่ต้องรู้ไว้:

กับดักในการออกแบบเทสต์

ในกราฟเหล่านั้น node ที่ถูกใช้ซ้ำเป็น leaf เสมอ — และ leaf ไม่มี _backward ที่ทำอะไรเลย การเรียกมันผิดลำดับจึงไม่ทำให้อะไรผิด
จะเห็นบั๊กได้ ต้องให้ node กลาง (ที่มี _backward จริง) เป็นตัวที่ถูกใช้ซ้ำ

กราฟที่ออกแบบมาให้พังโดยเฉพาะ:

x = 2.0   y = 3.0   p = 5.0   q = 7.0

m = x * y      →    6.0      ← node กลาง ที่มีพ่อแม่สองตัว
a = m * p      →   30.0
b = m * q      →   42.0
d = a * b      → 1260.0

m มีพ่อแม่คือ a และ b — ทั้งคู่ต้องทำงานเสร็จก่อน m ถึงจะเรียก _backward() ได้

บันทึก node ที่ต้นลูป = pre-order = ผิด

ลำดับที่ได้จาก trace() เดิม (บันทึก node ก่อน เข้าลูป):

d,  a,  m,  x,  y,  p,  b,  q
        ↑                   ↑
        m อยู่ตำแหน่ง 2      b อยู่ตำแหน่ง 6

b เป็นพ่อของ m แต่ b มาทีหลัง — ละเมิด invariant สาเหตุตรงไปตรงมา: DFS ดิ่งลงกิ่งของ a จนสุดก่อน ระหว่างทางเจอ m ก็บันทึกทันที ทั้งที่ b ยังไม่ได้แตะเลย

ผลลัพธ์เมื่อเรียกตามลำดับนั้น

nodeค่าที่ถูกค่าที่ได้
m.grad420420ถูก — เพราะสุดท้าย b ก็ได้ทำงาน
x.grad1260630ครึ่งเดียว
y.grad840420ครึ่งเดียว

อาการที่ต้องจำ: node ที่ถูกใช้ซ้ำเองกลับได้ค่าถูก แต่ลูกของมันได้ครึ่งเดียว เพราะตอน m._backward() ทำงาน m.grad เก็บมาแค่เส้นทางเดียว ส่วนอีกเส้นมาถึงทีหลัง — สายเกินไป

และเหมือนเดิม: ไม่มี error ไม่มี warning

บันทึก node ที่ท้ายลูป = post-order = กลับด้านแล้วได้คำตอบ

ย้ายบรรทัดบันทึกไปไว้หลังลูป — node จะถูกบันทึกตอนที่ลูกของมันเสร็จหมดแล้ว:

x,  y,  m,  p,  a,  q,  b,  d      ← ลูกมาก่อนพ่อ ทุกคู่

นี่คือด้านตรงข้ามของที่ต้องการพอดี — ซึ่งแปลว่าใกล้แล้ว reversed() ทีเดียวจบ และมันเป็น O(1) เพราะคืน iterator ไม่ได้ copy

สองจุดในฟังก์ชันเดียว ที่ทำคนละหน้าที่ 
def f(node):
    ┌── จุดที่ 1 ──┐   "ฉันเริ่มทำ node นี้แล้ว อย่าเข้ามาอีก"    → visited set

    for n in node._prev:
        f(n)

    └── จุดที่ 2 ──┘   "ลูกฉันเสร็จหมดแล้ว จองที่ในลำดับได้"     → order

เหตุผลที่ต้องมีสองโครงสร้าง ไม่ใช่เพราะอยากได้ที่เก็บสองที่ — แต่เพราะต้องบันทึกสองช่วงเวลาที่ต่างกัน โครงสร้างเดียวเลือกเวลาได้เวลาเดียว แล้วจะเสียงานอีกอย่างเสมอ

ลำดับที่ถูกต้อง มีได้หลายอัน

คำถามที่โผล่มาระหว่างทาง: ทำไม DFS ถึงเดินเข้า m ก่อน p? คำตอบอยู่ใน _prev — มันคือ [self, other] เขียน a = m * p ก็ได้ [m, p] · เขียน a = p * m ก็ได้ [p, m]

สลับแล้วได้ลำดับคนละอัน แต่ assert ยังผ่านทั้งคู่ — เพราะ topological order ไม่ได้มีคำตอบเดียว มันคือเซตของลำดับที่ทุกอันถูกต้องเท่ากัน ขอแค่ “พ่อมาก่อนลูก” ครบทุกเส้น

ผลข้างเคียงที่สำคัญกว่า: เทสต์ต้องเช็คคุณสมบัติ ไม่ใช่เช็คว่าตรงกับลำดับที่คิดไว้ เทสต์ที่ hard-code ลำดับเดียวจะพังทันทีที่สลับ m * p เป็น p * m ทั้งที่โค้ดยังถูกอยู่ 

pos = {id(n): i for i, n in enumerate(order)}
for child, parent in edges:
    assert pos[id(parent)] < pos[id(child)]

visited set ไม่ใช่ที่เก็บของ — หลักฐานที่วัดได้

ความสับสนที่กินเวลานานที่สุดของวัน: set ที่ใช้กันของซ้ำในผลลัพธ์ กับ set ที่ใช้กันเดินซ้ำ — มันคนละปัญหากัน

วัดบนกราฟ v = v + v ซ้ำ 16 ชั้น — มี node จริงแค่ 17 ตัว:

guardcontainerf() callsเก็บได้ซ้ำไหมเวลา
ไม่มีlist131,071131,071ซ้ำ13.2 ms
ไม่มีset131,07117ไม่ซ้ำ13.2 ms
มีlist3317ไม่ซ้ำ0.0 ms
มีset3317ไม่ซ้ำ0.0 ms

แถวที่ 2 คือหลักฐานทั้งหมด — เปลี่ยน list เป็น set แล้ว:

  • ของที่เก็บ 131,071 → 17 ✅ ข้อมูลถูกทันที
  • จำนวน call 131,071 → 131,071 ❌ ไม่ลดลงแม้แต่ call เดียว
  • เวลา 13.2 ms → 13.2 ms ❌ เท่าเดิมเป๊ะ

set ยืนอยู่ปลายทาง แล้วโยนของซ้ำทิ้งตอนจะเก็บ — โปรแกรมยังเดินเข้าไปทุกกิ่งเหมือนเดิม มันไม่ได้ลดงานเลย ส่วน guard ลด call จาก 131,071 เหลือ 33 = 4,000 เท่า ซึ่ง set ทำให้ไม่ได้

เรื่องคำศัพท์

“dedup ที่ container” กับ “dedup ที่ traversal” เป็นคำที่ใช้สอนกันเองในโปรเจกต์นี้เท่านั้น ไม่ใช่ศัพท์จริง อย่าเอาไปใช้ตอนสัมภาษณ์
ศัพท์สากลของอันหลังคือ visited set — ส่วนอันแรกไม่มีชื่อพิเศษ แค่บอกว่า “ใช้ set”

ใช้ order เป็น guard เลยได้ไหม

บทเรียนแถมเรื่องการวัดผล

เบนช์มาร์กรอบแรกของหัวข้อนี้ไม่เห็นความต่างเลย เพราะสร้างกราฟเป็นเส้นยาว ทำให้ order ว่างเกือบตลอดตอน scan — รูปทรงของข้อมูลเปลี่ยนคำตอบของคำถาม “อันไหนเร็วกว่า” ได้ ต้องวัดบนรูปทรงที่จะใช้จริงเสมอ
