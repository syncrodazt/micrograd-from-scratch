วันที่ไม่มีคณิตศาสตร์ใหม่เลยแม้แต่บรรทัดเดียว — มีแต่การจัดระเบียบว่าอะไรอยู่นาน อะไรเกิดใหม่ทุกครั้ง

2026-08-11 · Day 5 · เฟส 4 ขั้นแรก

คำถามที่ปลดล็อกทั้งไฟล์

“เรายังไม่มี x แล้วจะคูณ w กับ x ยังไง”

คำตอบคือ ไม่ต้องคูณตอนนั้น — งานของ Neuron แบ่งเป็นสองช่วงเวลาที่ไม่เกี่ยวกัน

ทำอะไรอยู่นานแค่ไหนเรียกว่า
__init__ สร้าง w กับ b ตลอดชีวิตของ neuron parameter
__call__ เอา w มาเจอ x แล้วคำนวณ เกิดใหม่ทุกครั้ง แล้วทิ้ง activation / ตัวกลาง

x ไม่มีตอน __init__ เพราะมันไม่ควรมี — neuron ตัวเดียวกันต้องรับ input ได้หลายชุดตลอดการเทรน ถ้า x ฝังอยู่ในตัวมัน ก็เรียกซ้ำด้วยข้อมูลใหม่ไม่ได้

__call__ 
class Greeter:
    def __init__(self, name):     # รันครั้งเดียว ตอนสร้าง object
        self.name = name

    def __call__(self, mood):     # รันทุกครั้งที่ใส่วงเล็บ
        return f"{mood}, {self.name}!"

g = Greeter("world")
g("hello")     → "hello, world!"
g("goodbye")   → "goodbye, world!"     object เดิม เรียกใหม่ได้เรื่อยๆ

dunder ตระกูลเดียวกับ __add__, __mul__, __repr__ ที่เขียนมาแล้ว — ต่างกันแค่มันผูกกับวงเล็บแทนเครื่องหมายคณิตศาสตร์

และเส้นแบ่ง parameter / ตัวกลาง คือนิยามของ parameters() พอดี — มันคือรายการ “ของที่ต้องอัปเดตตอนเทรน” ไม่ใช่ “Value ทั้งหมดในเครือข่าย” ซึ่งมีเป็นพันตัวและตายทุกรอบ

ค่าเริ่มต้นของ weight — ผิดได้สองทาง

เล็กเกินไป: symmetry

ถ้า weight ทุกตัวเริ่มที่ศูนย์ (หรือค่าเดียวกันหมด) neuron ทุกตัวในชั้นจะเห็น input เดียวกัน ได้ gradient เท่ากัน อัปเดตเท่ากัน — แล้วเหมือนกันตลอดไป ชั้นที่มี 100 neuron ก็เรียนรู้ได้เท่ากับมี 1

ใหญ่เกินไป: saturation

วัดจริงกับ neuron ที่รับ 3 input ค่าประมาณ 1.0:

weight ประมาณztanh(z)tanh'(z)
0.10.30.291319.15e-01
1.03.00.995059.87e-03
5.015.01.000003.74e-13
20.060.01.000000.00e+00

tanh แบนที่ปลายทั้งสองข้าง — weight ใหญ่ → z ใหญ่ → tanh' เข้าใกล้ศูนย์ → gradient ที่ไหลย้อนกลับถูกคูณด้วยเกือบศูนย์ แถวสุดท้ายคือศูนย์จริงๆ ไม่ใช่เกือบ: เครือข่ายตายสนิท เรียนอะไรไม่ได้อีกเลย

uniform(-1, 1) จึงอยู่ตรงกลางพอดี — ต่างกันมากพอจะทำลาย symmetry และเล็กพอที่ tanh ยังอยู่ในช่วงที่ชัน (Xavier / He initialization เกิดมาเพื่อเลือกช่วงนี้ให้ถูกตามขนาดของชั้น — แต่นั่น M2)

zip ที่ตัดของทิ้งเงียบๆ

Neuron.__call__ จับคู่ weight กับ input ด้วย zip — แล้วเกิดเรื่องนี้ขึ้น: 

n = Neuron(3)
n([1.0, 2.0])        # ให้มาแค่ 2 input จาก 3

→ Value(data = 0.9689875274388016)
   ...ไม่มี error เลย
พฤติกรรมมาตรฐานของ zip

มันหยุดที่ตัวสั้นกว่า แล้วเงียบ — neuron ที่รอ 3 input ได้มา 2 ก็คำนวณต่อโดยแกล้งลืม weight ตัวสุดท้าย แล้วคืนตัวเลขที่ดูสมเหตุสมผลออกมา
รูปแบบเดียวกับบั๊กทุกตัวที่ไล่ล่ากันมาทั้งสัปดาห์: ผิดโดยไม่ส่งเสียง และใน MLP ลึกๆ จะไล่หาแทบไม่ได้

Python 3.10+ มีทางออกอยู่ในตัว:

zip(self.ws, xs, strict=True)

→ ValueError: zip() argument 2 is shorter than argument 1

เปลี่ยนตัวเลขผิดเงียบๆ ให้กลายเป็น error ที่ชี้จุดทันที ด้วยการพิมพ์เพิ่ม 14 ตัวอักษร

หลักการที่ใหญ่กว่าตัวอย่างนี้

ทุกครั้งที่ภาษาให้เลือกระหว่าง “ทำต่อไปเงียบๆ” กับ “หยุดแล้วบอก” — เลือกอย่างหลังเสมอ ถ้าไม่มีเหตุผลชัดเจนที่จะไม่เลือก
เดือนนี้เจอมาแล้วสามรูปแบบ: gradient ที่ทับกันเพราะ = แทน += · ลำดับ backward ที่ผิดแล้วให้ค่าครึ่งเดียว · และตอนนี้ zip ที่ตัดของทิ้ง ไม่มีอันไหนโยน error สักอัน

สำนวนที่ได้มาระหว่างทาง

จับคู่ขนาดของชั้นด้วย list ที่เลื่อนไปหนึ่งช่อง

zip([nin, *sizes], sizes)

[3, 4, 4, 1]        ← ขาเข้า
   [4, 4, 1]        ← ขาออก
→  (3,4) (4,4) (4,1)

แต่ละ layer ต้องรู้ ขนาดขาเข้า กับ ขนาดขาออก ของตัวเอง และขาเข้าของชั้นหนึ่งก็คือขาออกของชั้นก่อนหน้า — zip ที่หยุดเองตรงตัวสั้นกว่า ทำให้ตัวเกินท้ายหายไปโดยไม่ต้องสั่ง ไม่มีการคำนวณ index จึงไม่มีทาง off-by-one

สังเกตว่าคุณสมบัติเดียวกันของ zip — หยุดที่ตัวสั้นกว่าโดยไม่บ่น — เป็นทั้งบั๊กที่อันตรายในหัวข้อก่อนหน้า และเครื่องมือที่สะอาดในหัวข้อนี้ ไม่มีคุณสมบัติไหนดีหรือแย่ในตัวเอง มีแต่เหมาะหรือไม่เหมาะกับที่ที่ใช้

อ่าน comprehension ที่มี for สองชั้น

[p for neuron in self.neurons for p in neuron.parameters()]

เท่ากับ:

result = []
for neuron in self.neurons:          # for ตัวแรก = วงนอก
    for p in neuron.parameters():    # for ตัวที่สอง = วงใน
        result.append(p)             # นิพจน์หน้าสุด = สิ่งที่เก็บ

ลำดับของ for เรียงเหมือนโค้ดปกติทุกประการ — ที่สับสนคือนิพจน์ที่จะเก็บอยู่หน้าสุด ทั้งที่เกิดขึ้นท้ายสุด

ส่วน [(*l) for l in lists] ใช้ไม่ได้เพราะ generator ให้ผลได้ทีละหนึ่งค่าต่อรอบ — จะให้มันคายหลายค่าในรอบเดียวไม่ได้ตั้งแต่ต้น

เทสต์ที่ตรึงทั้งสายด้วยความสัมพันธ์เดียว

w_i.grad == b.grad × x_i

ทั้ง bias และ weight ทุกตัวอยู่ใต้ tanh ตัวเดียวกัน ตัวคูณที่ไหลลงมาจากข้างบนจึงเป็นตัวเดียวกันหมด สิ่งที่แยกพวกมันคือ input ที่แต่ละ weight ถูกคูณด้วยเท่านั้น

เทสต์ข้อเดียวนี้ตรวจทั้งเส้นทางตั้งแต่ output ย้อนกลับไปถึง parameter — และมันยังบอกเรื่องที่ใหญ่กว่านั้น: weight ที่ได้รับ input ค่ามาก จะได้ gradient มากตามสัดส่วน ซึ่งคือเหตุผลที่ input ที่ scale ต่างกันมากๆ ทำให้เครือข่ายเทรนยาก และเป็นที่มาของการ normalize ข้อมูลก่อนเทรน

เทสต์จับ regression ได้ในหนึ่งวินาที

ระหว่างแยกตรรกะห่อค่าออกมาเป็นเมธอดเดียว เงื่อนไขกลับด้าน:

return Value(x) if isinstance(x, Value) else x

ห่อของที่เป็น Value อยู่แล้ว และปล่อยตัวเลขธรรมดาไว้เฉยๆ — กลับกันพอดี 

67 failed, 18 passed

รู้ทันทีภายในวินาทีเดียว ถ้าไม่มีเทสต์ บั๊กนี้จะไปโผล่ตอนเขียน nn.py แล้วดูเหมือนปัญหาของ nn.py — ไล่ผิดที่ไปเป็นชั่วโมง

นี่คือเหตุผลที่ refactor ต้องมีเทสต์รองอยู่ก่อน ไม่ใช่ทำทีหลัง — refactor แปลว่า “เปลี่ยนรูปโดยไม่เปลี่ยนพฤติกรรม” ซึ่งเป็นคำกล่าวอ้างที่พิสูจน์ไม่ได้เลย ถ้าไม่มีอะไรคอยตรวจพฤติกรรม

ข้ออ้างที่ทำให้การเทรนเป็นไปได้

out = net(x)
out.backward()

for p in net.parameters():
    p.data -= 0.01 * p.grad      # เดินสวนทาง gradient

net(x)   →  น้อยลง

grad บอกว่า “ขยับ parameter ไปทางไหนแล้ว output จะเพิ่ม” — เดินสวนทางก็ได้ค่าที่ลดลง ทั้ง training loop คือบรรทัดนี้ ทำซ้ำ โดยเปลี่ยนจาก output ดิบเป็น loss

และมีเทสต์คู่แฝดที่เดินตาม gradient แล้วต้องได้ค่าเพิ่ม — ตรึงเครื่องหมายไว้ ถ้าเขียน gradient descent ผิดเครื่องหมาย เทสต์นั้นจะเป็นข้อที่ยังผ่านอยู่
