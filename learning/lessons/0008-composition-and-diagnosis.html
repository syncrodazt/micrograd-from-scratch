เพิ่ม operation โดยไม่เพิ่มกฎอนุพันธ์

เฟส 3 เพิ่ม operation แปดตัว — __neg__, __sub__, __pow__, __truediv__, exp และ reflected อีกสี่ตัว แต่ต้อง derive อนุพันธ์ใหม่จริงๆ แค่ สองตัว

operationต้องมีกฎ _backward ของตัวเอง?
__pow__ต้อง — k·x^(k−1)
expต้อง — และมันคือค่าของตัวเอง
__neg__ไม่ — คือคูณด้วย -1
__sub__ไม่ — คือบวกกับตัวที่ติดลบ
__truediv__ไม่ — คือคูณด้วยตัวที่ยกกำลัง -1
reflected ทั้งสี่ไม่ — เรียกตัวเดิมโดยสลับข้าง
ทำไมถึงได้ฟรี

เพราะ a - b ที่เขียนเป็น a + (-b) ไม่ได้เป็นแค่การคำนวณที่เท่ากัน — มันสร้างกราฟที่ประกอบจาก node ที่มี _backward ถูกต้องอยู่แล้ว
backward pass ไม่รู้เลยว่ามี “การลบ” อยู่ในโลก มันเห็นแค่บวกกับคูณ แล้วเดินตามกฎเดิม gradient จึงถูกโดยไม่ต้องมีใครสั่ง

ผลที่ตามมาสำคัญกว่าความสะดวก: ยิ่ง operation พื้นฐานน้อย ยิ่งมีที่ให้ผิดน้อย กฎอนุพันธ์ทุกข้อที่เขียนเองคือโอกาสพลาดหนึ่งครั้ง — สี่ตัวที่ประกอบเอาไม่มีโอกาสนั้นเลย

a * 2 ผ่าน ไม่ได้แปลว่า 2 * a ผ่าน

สองบรรทัดนี้ดูสมมาตร แต่เดินคนละเส้นทางในเครื่อง:

a * 2   →  Python ถามซ้ายก่อน  →  Value.__mul__(a, 2)      ✅
2 * a   →  Python ถามซ้ายก่อน  →  int.__mul__(2, a)        ❌ int ไม่รู้จัก Value
                                 →  ถอยไปถามขวา  →  Value.__rmul__(a, 2)

Reflected operator คือทางถอยที่ Python เตรียมไว้ — ฝั่งซ้ายตอบว่า NotImplemented เมื่อไหร่ มันจะไปถามฝั่งขวาด้วยเมธอดที่มี r นำหน้า

กับดักคือมัน เงียบจนกว่าจะเจอ — เขียน MLP ทั้งตัวโดยใช้ a * 2 ตลอด แล้ววันหนึ่งพิมพ์ 2 * a ครั้งเดียวก็ TypeError ทันที เทสต์ที่ครอบคลุมจึงต้องแยกเป็นคนละข้อ ไม่ใช่ข้อเดียว

Payoff: tanh ที่ประกอบจาก exp

tanh(x) = (e^{2x} − 1) / (e^{2x} + 1) — ประกอบจาก scalar multiply, exp, scalar add, subtract และ divide ทั้งหมดที่เพิ่งเขียน

tanh ตัวเดียวจบ0.46211715726000974

math.tanh(0.5)0.46211715726000974

ทั้งค่าและ gradient ตรงกัน — “จะแตกละเอียดแค่ไหน” เป็นทางเลือกด้านวิศวกรรม ไม่ใช่กฎของคณิตศาสตร์ แตกละเอียด = กฎน้อยลงแต่กราฟใหญ่ขึ้น · รวมเป็นก้อน = เร็วกว่าแต่ต้อง derive เอง PyTorch ก็เลือกแบบหลังสำหรับ operation ที่ใช้บ่อย

หลักสุดท้ายที่ไม่ตรงกัน

...0974 กับ ...097 — ถูกต้องทางคณิตศาสตร์เท่ากัน แต่ทศนิยมไม่เท่ากัน เพราะลำดับการคำนวณต่างกัน แต่ละขั้นก็ปัดคนละแบบ

“ไอ้ตัวนี้ จริงๆ แล้วมันคืออะไร ไม่ใช่สิ่งที่ฉันคิดว่ามันเป็น”
แล้วพิมพ์มันออกมาดู แทนที่จะไล่อ่านโค้ดในหัว

1. _backward ของ tanh ไม่ทำงาน แม้แต่ print ก็ไม่ออก

print(y._backward)
→ <function Value.__init__.<locals>.<lambda> at 0x...>      ← lambda: None ตัวเดิม!

print(a._backward)   # จาก a = Value(1.0) * Value(2.0)
→ <function Value.__mul__.<locals>._backward at 0x...>      ← ของจริง

ฟังก์ชันใน Python บอกได้ว่าตัวเองเกิดที่ไหน — Value.__mul__.<locals>._backward อ่านว่า “เกิดข้างใน __mul__” พอเห็นว่า tanh ยังถือ __init__.<locals>.<lambda> อยู่ ก็รู้ทันทีว่า print ไม่ออกเพราะ มันถูกเรียกแล้ว แต่ไปโดนฟังก์ชันคนละตัว

สาเหตุ: บรรทัด t._backward = _backward เยื้องเกินไปหนึ่งชั้น เลยไปอยู่ข้างใน closure ที่ไม่มีวันทำงาน — บั๊กที่กัดหางตัวเอง

ฟังก์ชันนี้เกิดที่ไหนf.__qualname__
มันจับตัวแปรอะไรไว้บ้างf.__code__.co_freevars

2. gradient ของ tanh ขาดตัวคูณ — แต่เทสต์ผ่าน

เทสต์แรกที่เขียนคือ:

x = Value(0.0)
y = x.tanh()     ← tanh อยู่นอกสุด → y.grad = 1.0 พอดี
y.backward()

คูณด้วย 1 ก็เหมือนไม่ได้คูณ — เทสต์ผ่านทั้งที่โค้ดผิด กับดักเดียวกับที่เจอตอน q = z*z ในวันที่ 2 เป๊ะ

เทสต์ที่มองเห็น ต้องให้ tanh ไม่ได้อยู่นอกสุด — ครอบด้วย y * y แล้ว gradient ที่ไหลเข้ามากลายเป็น 2y ไม่ใช่ 1

บทเรียนที่ต้องติดตัว: เทสต์ที่ operation อยู่นอกสุด มองไม่เห็นบั๊กเรื่องตัวคูณเลย ทุกครั้งที่เพิ่ม operation ใหม่ ให้เขียนอย่างน้อยหนึ่งเทสต์ที่มันถูกครอบอยู่

Operator คือภาษากลาง method คือภาษาถิ่น

ตอนเขียนเทสต์เทียบกับ numerical gradient เจอว่า math.tanh(a) พัง แต่ a * b + c ไม่พัง ทั้งที่ a เป็น Value เหมือนกัน:

นิพจน์ต้องการfloatValue
a * b + c__mul__, __add__✅✅
math.tanh(a)เป็นตัวเลขจริง✅❌

operator overloading คือสิ่งที่ทำให้ Value พูดภาษาเดียวกับ float ได้ ส่วนเมธอดไม่ใช่ — เพราะงั้น harness ที่ต้องรันนิพจน์เดียวกันทั้งสองโลก ต้องเก็บ callable สองตัว ต่อหนึ่งเคส ตัวหนึ่งพูดภาษา Value อีกตัวพูดภาษา float

ตอนออกแบบครั้งแรกพลาดเพราะตั้งชื่อว่า f กับ v ซึ่งไม่บอกว่าตัวไหนอยู่โลกไหน พอสลับตำแหน่งกันก็ยังอ่านดูเหมือนถูก · เปลี่ยนเป็น on_values / on_floats แล้วการสลับกลายเป็นเรื่องที่เห็นด้วยตาเปล่า — ชื่อที่ดีกำจัดบั๊กทั้งประเภท ไม่ใช่แค่ครั้งเดียว

Decorator มีสองชนิด

@ เป็นน้ำตาลของบรรทัดเดียว:

@foo
def bar(): ...

# เท่ากับ:  bar = foo(bar)
ชนิดคืนอะไรตัวอย่าง
ห่อฟังก์ชันตัวใหม่ที่เปลี่ยนพฤติกรรม@functools.cache
แปะป้ายตัวเดิม แค่ติดข้อมูลไว้@pytest.mark.parametrize

ของจริงที่ pytest แปะไว้:

demo.pytestmark  →  [Mark(name='parametrize', args=('x', [1, 2, 3]), kwargs={})]
demo(5)          →  5                    ← พฤติกรรมไม่ถูกแตะเลย

ทำได้เพราะ ฟังก์ชันใน Python เป็น object ที่มี __dict__ เหมือนของอื่น — fn.anything = ... ได้เลย · โครงเดียวกับ t._backward = _backward ที่ทำมาตั้งแต่วันที่สอง แค่กลับทิศ

parametrize ทั้งอันใน 6 บรรทัด

def parametrize(names, rows):
    names = [n.strip() for n in names.split(",")]     # "a, b" → ["a", "b"]
    def attach(fn):
        fn.params = (names, rows)
        return fn
    return attach

แล้วสิ่งที่ pytest ทำตอนเก็บเทสต์:

names, rows = show.params
for row in rows:
    kwargs = dict(zip(names, row))     # ←←← string กลายเป็น argument ตรงนี้
    show(**kwargs)

zip จับคู่ชื่อกับค่าตามตำแหน่ง แล้ว ** คลี่ dict เข้าไปเป็น keyword argument — เหตุผลที่ต้องส่งชื่อมาเป็น string คือ pytest ต้องแยกให้ออกว่า argument ตัวไหนมาจาก parametrize และตัวไหนมาจาก fixture

วิธีแก้ที่กลายเป็นปัญหาเสียเอง

TYPE_CHECKING at runtime is False        ← มันไม่เคยทำงานตอนรันจริง
