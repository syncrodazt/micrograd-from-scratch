# 0002 — recursion คือสัญญา ไม่ใช่ลำดับการทำงาน

**วันที่:** 2026-08-08
**สถานะ:** ใช้แก้ปัญหาจริงได้แล้ว

## บริบท

ไม่เคยเขียน tree recursion มาก่อน (พื้นฐานเป็น control engineering)
พยายามเขียน `trace()` โดยไล่ลำดับการทำงานในหัว:

```
[d]
[d, c]
[d, c, a*b]
[d, c, a*b, a, b]
```

วิธีนี้ทำให้เขียนโค้ดไม่ออก เพราะต้องถือ state หลายชั้นไว้ในหัวพร้อมกัน

## สิ่งที่พบ

การไล่ execution ในหัวคือ **มุมมองที่ผิด** มุมที่ถูกคือมองเป็น *สัญญา*:

```
f(a)   = ?     ← leaf ตอบได้เลย
f(a*b) = ?     ← ในรูปของ f(a) และ f(b)
f(d)   = ?     ← ในรูปของ f(a*b) และ f(c)
```

เขียนสามบรรทัดนี้ให้สอดคล้องกันก่อน แล้วโค้ดจะเขียนตัวเอง

## กรอบ 4 ข้อ

1. สัญญาว่าจะคืนอะไร (เขียนเป็นประโยคก่อนแตะคีย์บอร์ด)
2. base case — เคสไหนตอบได้ทันที
3. recursive case — **สมมติว่าลูกทำงานถูกแล้ว** ฉันเพิ่มอะไร
4. รวมยังไงให้ตรงกับสัญญาข้อ 1

## บั๊กที่เกิดจากการข้ามข้อ 1

- base case คืน `[]` ทิ้ง node ตัวเองไป → leaf หายหมด
- recursive case `append` list ทั้งก้อนเป็นสมาชิกเดียว → list ซ้อน list

ทั้งสองคือ**อาการเดียวกัน**: base case กับ recursive case คืนของคนละชนิด

## สะพานจากพื้นฐานเดิม

- recursion = **induction** — พิสูจน์ base + step แล้วจบ ไม่ต้องไล่ทีละ k
  (เหมือนพิสูจน์ stability)
- รูปเดียวกับ **Bellman equation** `V(s) = r(s) + Σ V(s')` — ไม่มีใครไล่คำนวณ V ทุก state ในหัว
